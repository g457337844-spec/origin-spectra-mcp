# Contributing

Open an issue describing the expected behavior, actual behavior, software versions, and a minimal reproducible example before proposing a substantial change. Use synthetic or explicitly shareable data; do not upload credentials, proprietary libraries, commercial reference databases, or private research results.

Keep changes focused, preserve upstream attribution, and describe the checks you ran. Follow the development and verification commands in README.md. Mark tests requiring licensed desktop applications separately; an offline test pass does not establish live application compatibility.

For a potentially exploitable security problem, avoid posting secrets or exploit details in a public issue. Use GitHub's private vulnerability reporting if enabled; otherwise open a minimal issue requesting a private contact channel without sensitive details.
